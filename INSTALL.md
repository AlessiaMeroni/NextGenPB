# INSTALL — Building and Running This Project
 
This file documents how to build and run the code developed for this
project: **Mesh repartitioning for load balancing of surface and volume
calculations in NextGenPB**. It only covers what is specific to this
project (the `--strategy` flag, the two new load-balancing strategies,
and how to verify a run) on top of a standard NextGenPB installation.
 
Two platforms were used to develop and validate this project, and both
sets of instructions below are verified, step by step, exactly as
written: a laptop/workstation running Ubuntu 24.04, and the HPC cluster
of the Department of Mathematics of Politecnico di Milano. Pick the
section that matches your setup.
 
**Source code:** this repository, branch `mesh-repartitioning`
(https://github.com/AlessiaMeroni/NextGenPB, branch `mesh-repartitioning`).

## 1. Installing on a Laptop or Workstation (Ubuntu 24.04)
 
NextGenPB depends on several external libraries, which must be built in
the order given below, since each later step depends on the ones before
it.
 
### 1.1 System dependencies
 
```bash
sudo apt-get install -y build-essential gfortran cmake openmpi-bin \
    libopenmpi-dev libboost-all-dev libp4est-dev libmumps-dev \
    libscotch-dev octave octave-dev libtbb-dev libcgal-dev \
    libqhull-dev libarpack2-dev libjansson-dev
```
 
This installs, among others, Boost 1.83.0, CGAL 5.6-1build3, and Octave
8.4.0 (with development headers) as packaged for Ubuntu 24.04.
 
### 1.2 NanoShaper (molecular surface generation)
 
Not a well-known library outside computational biophysics — source and
documentation: https://gitlab.iit.it/SDecherchi/nanoshaper
 
```bash
git clone https://gitlab.iit.it/SDecherchi/nanoshaper.git
cd nanoshaper
cp CMakeLists_so.txt CMakeLists.txt
mkdir build_lib && cd build_lib
cmake .. -DCMAKE_BUILD_TYPE="Release"
make -j$(nproc)
```
 
### 1.3 LIS 2.1.6 (iterative linear solver)
 
Source and documentation: https://www.ssisc.org/lis/
 
```bash
wget https://www.ssisc.org/lis/dl/lis-2.1.6.zip && unzip lis-2.1.6.zip
cd lis-2.1.6
./configure --prefix="$HOME/libs/lis" --enable-mpi --enable-shared
make -j$(nproc) && make install
```
 
### 1.4 octave_file_io 1.0.91
 
Source: https://github.com/carlodefalco/octave_file_io
 
```bash
wget https://github.com/carlodefalco/octave_file_io/archive/refs/tags/v1.0.91.tar.gz
tar -xf v1.0.91.tar.gz && cd octave_file_io-1.0.91
./autogen.sh && mkdir build && cd build
../configure --prefix="$HOME/libs/octave_file_io" \
  CPPFLAGS="-I/usr/include/octave-8.4.0" \
  LDFLAGS="-L/usr/lib/x86_64-linux-gnu/octave/8.4.0 \
           -Wl,-rpath,/usr/lib/x86_64-linux-gnu/octave/8.4.0"
```
 
**Known issue:** the `Makefile` generated by `mkoctfile` at this point
contains two malformed linker-flag lines, `OCTAVE_LINK_ADD = -L` and
`liboctave_file_io_la_LIBADD = -L`, each with an empty `-L` path that
causes `libtool` to fail (`"need path for '-L' option"`). Remove both
lines before building:
 
```bash
sed -i '/^OCTAVE_LINK_ADD = -L$/d' Makefile
sed -i '/^liboctave_file_io_la_LIBADD = -L$/d' Makefile
make -j$(nproc) && make install
```
 
### 1.5 bim++ (finite-element library)
 
Source: https://github.com/carlodefalco/bimpp — links against MUMPS
(https://mumps-solver.org) as an alternative direct solver to LIS.
 
```bash
wget https://github.com/carlodefalco/bimpp/archive/refs/tags/NextGenPB-v0.0.01.tar.gz
tar -xvzf NextGenPB-v0.0.01.tar.gz && cd bimpp-NextGenPB-v0.0.01
mkdir build && ./autogen.sh && cd build
../configure --prefix="$HOME/libs/bimpp" \
  CPPFLAGS="-I$HOME/libs/octave_file_io/include" \
  --with-octave_file_io-home="$HOME/libs/octave_file_io" \
  --with-lis-home="$HOME/libs/lis" \
  --with-p4est-home=/usr/lib/x86_64-linux-gnu \
  --with-mumps-home=/usr/lib/x86_64-linux-gnu
make -j$(nproc) && make install
```
 
The `configure` script locates `p4est`, LIS, and MUMPS automatically
from the system package paths; only `octave_file_io`, installed to a
custom prefix in the previous step, needs its path given explicitly.
 
### 1.6 Compiling this project
 
```bash
git clone -b mesh-repartitioning https://github.com/AlessiaMeroni/NextGenPB.git
cd NextGenPB
cp local_setting/local_settings_ubuntu.mk src/local_settings.mk
```
 
Edit `src/local_settings.mk` so that every library path points to the
installation prefixes used above (`$HOME/libs/lis`,
`$HOME/libs/octave_file_io`, `$HOME/libs/bimpp`, and the NanoShaper
build directory), and add the following linker flag, needed for the
dynamic linker to locate `liboctinterp.so.11` at runtime:
 
```make
LDFLAGS += -Wl,-rpath,/usr/lib/x86_64-linux-gnu/octave/8.4.0
```
 
Then compile:
 
```bash
cd src && make clean all
```
 
The executable `ngpb` is created inside `src/`.

## 2. Installing on the Cluster (Department of Mathematics HPC)
 
The cluster requires its own installation, independent of the laptop
one: different default compiler, different library versions and paths,
and no `sudo` access. The commands below assume access to the cluster
of the Department of Mathematics of Politecnico di Milano and a valid
account.
 
### 2.1 Connecting and requesting a compute job
 
```bash
. /etc/profile.d/pbs.sh
qsub -I -q cpu -l select=1:ncpus=4:mpiprocs=4:host=cpu04
```
 
The `cpu` queue allows up to 48 hours, needed for compilation; the
`scalability` queue (up to 112 cores, 30-minute limit) is for
performance runs and is not needed for installation.
 
### 2.2 Source code
 
```bash
mkdir -p /scratch_local/$(whoami)
cd /scratch_local/$(whoami)
git clone -b mesh-repartitioning https://github.com/AlessiaMeroni/NextGenPB.git
```
 
### 2.3 Compiler: the system GCC, not the one Spack provides
 
```bash
source /software/spack/share/spack/setup-env.sh
export PATH=$(echo $PATH | tr ':' '\n' | grep -v spack | tr '\n' ':')
gcc --version   # must report 13.3.0 (Ubuntu), not a Spack GCC
```
 
The system compiler (GCC 13.3.0) is required for compatibility with
CGAL 5.6 and with Octave/ncurses' C++ interfaces; GCC 15.2.0, loaded by
Spack by default, fails to compile both.
 
### 2.4 Octave with development headers (personal Spack instance)
 
The cluster's system Octave package works but does not ship
`mkoctfile` or C++ headers. Install a personal copy through Spack
(https://spack.io), using the system compiler:
 
```bash
git clone -c feature.manyFiles=true --depth=100 \
    https://github.com/spack/spack.git ~/spack
source ~/spack/share/spack/setup-env.sh
spack compiler find
spack install octave %gcc@13.3.0
export OCTAVE_ROOT=~/spack/opt/spack/linux-cascadelake/octave-9.4.0-*
```
 
### 2.5 NanoShaper
 
```bash
mkdir -p ~/cluster-libs && cd ~/cluster-libs
git clone https://gitlab.iit.it/SDecherchi/nanoshaper.git
cd nanoshaper && cp CMakeLists_so.txt CMakeLists.txt
mkdir -p build_lib && cd build_lib
cmake .. -DCMAKE_BUILD_TYPE="Release" \
  -DCMAKE_C_COMPILER=/usr/bin/gcc-13 -DCMAKE_CXX_COMPILER=/usr/bin/g++-13 \
  -DCGAL_DIR=/usr/lib/x86_64-linux-gnu/cmake/CGAL \
  -DBOOST_ROOT=<path to Boost 1.88.0 in the shared Spack instance, \
                from `spack find -lv boost`> \
  -DBoost_NO_SYSTEM_PATHS=TRUE
make -j$(nproc)
```
 
The explicit `CGAL_DIR` works around a path-resolution issue (`/lib` is
a symlink to `/usr/lib` on this Ubuntu-based system, which offsets
CMake's internal search logic for `CGALConfig.cmake` by one level).
`BOOST_ROOT` points to Boost 1.88.0, already installed in the cluster's
*shared* Spack instance, because the system Boost package does not
provide the `boost_filesystem` CMake config target.
 
> **Note:** this Boost version differs from the laptop's (1.83.0), which
> produces a very slightly different molecular-surface triangulation on
> the two platforms — a known platform effect. It does not affect
> correctness, and results on a given platform should only be compared
> against reference values from that same platform.
 
### 2.6 LIS 2.1.6 and octave_file_io 1.0.91
 
```bash
# LIS
cd ~/cluster-libs
wget https://www.ssisc.org/lis/dl/lis-2.1.6.zip && unzip lis-2.1.6.zip
cd lis-2.1.6
CC=/usr/bin/mpicc CXX=/usr/bin/mpicxx ./configure \
  --prefix="$HOME/cluster-libs/lis" --enable-mpi --enable-shared
make -j$(nproc) && make install
 
# octave_file_io
cd ~/cluster-libs
wget https://github.com/carlodefalco/octave_file_io/archive/refs/tags/v1.0.91.tar.gz
tar -xf v1.0.91.tar.gz && cd octave_file_io-1.0.91
./autogen.sh && mkdir build && cd build
../configure --prefix="$HOME/cluster-libs/octave_file_io" \
  LDFLAGS="-L$OCTAVE_ROOT/lib/octave/9.4.0 -Wl,-rpath,$OCTAVE_ROOT/lib/octave/9.4.0" \
  --with-octave-home="$OCTAVE_ROOT/bin" CC=/usr/bin/mpicc CXX=/usr/bin/mpicxx
make -j$(nproc) && make install
```
 
Both libraries are configured with the MPI compiler wrappers
(`mpicc`/`mpicxx`) directly, using their absolute paths — required
because the cluster's `mpicxx` wrapper otherwise falls back to
whichever GCC is first on `PATH`, which may still be Spack's if any
Spack entry was left in place. `make install` is required (not just
`make`) before proceeding to the next step, as bim++'s `configure`
looks for `octave_file_io.h` under the installed prefix, not the build
directory.
 
### 2.7 bim++
 
```bash
cd ~/cluster-libs
wget https://github.com/carlodefalco/bimpp/archive/refs/tags/NextGenPB-v0.0.01.tar.gz
tar -xvzf NextGenPB-v0.0.01.tar.gz && cd bimpp-NextGenPB-v0.0.01
mkdir build && ./autogen.sh && cd build
../configure --prefix="$HOME/cluster-libs/bimpp" \
  CPPFLAGS="-I/usr/include -I$OCTAVE_ROOT/include/octave-9.4.0/octave \
            -I$HOME/cluster-libs/octave_file_io/include \
            -DOMPI_SKIP_MPICXX -DHAVE_OCTAVE_44 -DBIM_TIMING" \
  LDFLAGS="-L/usr/lib/x86_64-linux-gnu -L$OCTAVE_ROOT/lib/octave/9.4.0 \
           -Wl,-rpath,$OCTAVE_ROOT/lib/octave/9.4.0" \
  --with-blas-lapack="-lopenblas" \
  --with-octave_file_io-home="$HOME/cluster-libs/octave_file_io" \
  --with-octave-home="$OCTAVE_ROOT/bin" \
  --with-p4est-home=/usr/lib/x86_64-linux-gnu \
  --with-lis-home="$HOME/cluster-libs/lis" \
  --with-mumps-home=/usr/lib/x86_64-linux-gnu \
  F77=/usr/bin/mpif90 CXX=/usr/bin/mpicxx MPICC=/usr/bin/mpicc CC=/usr/bin/mpicc \
  --with-mumps-extra-libs="-L/usr/lib -L/usr/lib/x86_64-linux-gnu -lscotch -lmpi -lopenblas -lgfortran"
nohup bash -c 'make -j$(nproc) && make install' > ~/bimpp_build.log 2>&1 &
```
 
All three of the more delicate dependencies (p4est, LIS, MUMPS) are
located and linked correctly without further intervention, thanks to
the system packages already present on the cluster. Running the build
under `nohup ... &` is deliberate: SSH sessions on this infrastructure
are subject to unexpected disconnections, and a long build left in the
foreground would otherwise be lost; check `~/bimpp_build.log` for
progress or completion.
 
### 2.8 `local_settings.mk` and compiling this project
 
Use the same structure as the laptop's `local_settings.mk` (Section
1.6 above), with the cluster paths (`~/cluster-libs/...`) in place of
the system Ubuntu ones, plus two additions required for BLAS/LAPACK to
resolve correctly at runtime:
 
```make
LDFLAGS+= -L/usr/lib/x86_64-linux-gnu/openblas-pthread \
          -Wl,-rpath,/usr/lib/x86_64-linux-gnu/openblas-pthread
LIBS+= -Wl,--no-as-needed -L/usr/lib/x86_64-linux-gnu/openblas-pthread \
       -lopenblas -Wl,--as-needed
```
 
The cluster hosts two mutually incompatible BLAS/LAPACK installations
(a generic reference one, and a multi-threaded optimized one under
`openblas-pthread/`); without these two lines, linking fails with
undefined internal BLAS/LAPACK symbols, and even after fixing only the
link step, the executable still fails at runtime (`--no-as-needed` is
required because the modern linker otherwise discards libraries that
are not called directly by the executable, only indirectly through
MUMPS).
 
```bash
cd /scratch_local/$(whoami)/NextGenPB/src
export LD_LIBRARY_PATH=/usr/lib/x86_64-linux-gnu/openblas-pthread:$LD_LIBRARY_PATH
nohup make clean all > ~/nextgenpb_build.log 2>&1 &
```

## 3. Running the Code
 
The executable is invoked with MPI, and accepts a `--strategy` flag —
**the option added by this project** — on top of the standard
NextGenPB arguments:
 
```bash
mpirun -np <N> /path/to/NextGenPB/src/ngpb \
    --prmfile options.prm --strategy <unbalanced|balanced_embedded|balanced_indexed>
```
 
* `unbalanced` — the original, unmodified strategy: no redistribution,
  each rank computes the surface energy only on the border quadrants it
  happened to find during mesh marking.
* `balanced_embedded` — this project's first strategy: border-quadrant
  packets are redistributed evenly across ranks, with $\varphi$/$\varepsilon$
  embedded directly in each packet.
* `balanced_indexed` — this project's second strategy: same
  redistribution, but packets carry only global node indices, and
  $\varphi$/$\varepsilon$ are fetched separately, by index, after
  redistribution.
If `--strategy` is omitted, `balanced_indexed` is used by default. All
three strategies are numerically equivalent (verified to at least 10
significant digits across every configuration tested, from 1 to 112 MPI
ranks); they differ only in performance, not in the physics computed.
 
On the cluster, for rank counts above the `cpu` queue's limit (28
cores), request a job on the `scalability` queue instead (up to 112
cores, one full node, 30-minute limit):
 
```bash
qsub -I -q scalability -l select=1:ncpus=112:mpiprocs=112:host=cpu04
```

## 4. Verifying the Installation (Quick Test)
 
The `data/` directory of this repository includes example molecular
structures, including protein 1CCM (642 atoms) used as the reference
molecule throughout this project. To confirm the installation works
end to end, create a working directory with the baseline parameter
file below and run the simplest possible simulation.
 
**`options.prm`:**
 
```ini
[mesh]
mesh_shape = 0
perfil1 = 0.95
perfil2 = 0.2
scale   = 2.0
[../]
 
[model]
bc_type = 1
molecular_dielectric_constant = 2
solvent_dielectric_constant   = 80
ionic_strength                = 0.145
T                              = 298.15
calc_energy    = 2
calc_coulombic = 1
[../]
```
 
**Run** (from a directory containing `options.prm` and `1CCM.pqr`,
copied from `data/`):
 
```bash
mpirun -np 4 /path/to/NextGenPB/src/ngpb \
    --prmfile options.prm --pqrfile 1CCM.pqr --strategy unbalanced
```
 
**Expected output** (terminal log, last lines):
 
```
  Polarization energy [kT]:                          -384.617...
  Direct ionic energy [kT]:                           -0.252...
  Coulombic energy [kT]:                          -10097.242...
  Sum of electrostatic energy contributions [kT]: -10482.110...
```
 
A successful run should reproduce the total energy above (small
differences beyond the reported digits are normal, and are due to
floating-point summation order). Repeat the same run with
`--strategy balanced_embedded` and `--strategy balanced_indexed`: the
total energy should match the `unbalanced` run to at least 10
significant digits in every case; the terminal log for the two balanced
strategies additionally reports a `Redistribute border quad` timing
line, absent for `unbalanced`.

## 5. Output Files
 
Depending on the options enabled in `options.prm`, a run also writes,
to the working directory:
 
* `.vtu` / `.pvtu` — dielectric map and electrostatic potential on the
  3D grid, one file per MPI rank plus a master file referencing all of
  them; readable in ParaView.
* `phi_surf.txt` — surface mesh points with the potential computed
  there.
* `phi_nodes.txt` — boundary nodes of the computational domain with
  the potential computed there.
* `phi_on_atoms.txt` — atomic centers with the potential computed at
  those positions.
`scripts/vtu2cube.py` (in the repository) converts the `.vtu` output
into the Gaussian `.cube` format understood by PyMOL, VMD, and
ChimeraX, e.g.:
 
```bash
python3 scripts/vtu2cube.py 1CCM_out.pqr --scale 2
```
